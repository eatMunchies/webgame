# Table of Salem

A Town of Salem style social deduction game, played around one table with a phone or laptop each, in a top-down RPG town that runs in the browser. The repo and the code still call it `webgame`. The window and app are named Table of Salem, but saves stay in the `webgame` folder (`application/config/custom_user_dir_name` in `front/project.godot`), so renaming the game kept existing profiles.

How the game looks and why (palette, type, components, when to use a dialog) is in [docs/DESIGN.md](docs/DESIGN.md), and the story behind it in [docs/LORE.md](docs/LORE.md).

## Layout

| Path | Purpose |
|------|---------|
| `front/` | Game client (Godot 4.7 project, exported to the web) |
| `rust/` | Rust workspace: the shared protocol, the game engine, the game server, the client logic both clients share, a terminal test client, and the GDExtension the Godot client loads |
| `api/auth/` | Authentication service |
| `api/db/` | Database |
| `assets/` | Art assets (see below) |

## Game client (`front/`)

Requires [Godot 4.7](https://godotengine.org/download) (the standard build, not .NET), [Rust](https://rustup.rs), and [just](https://github.com/casey/just). The project uses the Compatibility renderer because the web export requires it, and renders at 320x180, scaled up by whole numbers with no texture filtering so pixel art stays sharp.

### Building the Rust extension

The client loads a GDExtension built from `rust/crates/webgame-godot-rust`. Godot doesn't compile it, so build it before opening the project for the first time and again after changing Rust code:

```sh
just build
```

The editor picks up the rebuilt library on its own. Run `just` with no arguments to list every recipe. To check the UI without a screen, `just shots 405x720 --name=Ada --create` plays the game in a virtual display and saves a screenshot every few seconds to `front/reports/shots` (see `front/tools/shoot.gd`; needs `xvfb-run`).

Machine-specific settings go in a `.env` file at the repo root, which is gitignored. Copy `.env.example` to `.env` and fill in what applies to you: `GODOT` if Godot isn't on your PATH, and `EMSDK` for web builds (see below).

### Running

To work in the editor, open Godot's Project Manager, choose Import, and select `front/project.godot`. Press F5 to run.

The window opens at 1920x1080. The game starts on the Table of Salem screen, a plaza where you walk around your own house (any house layer you haven't picked shows as a random style, and your name is over the roof) on an endless checkerboard floor that fades into haze (`scripts/plaza_floor.gd`, drawn by `shaders/plaza_floor.gdshader`). An invisible ring keeps you near the house. Click or tap the house to open the customizer (E at its door works too). A hint over the house says "> click to customize" (on a touch screen, "> tap to customize") in the machine's cyan while you're near it. On a portrait screen like a phone's the customizer lays out for 720x1280, with the character on its pedestal above the tabs, bigger tiles, and each row of tiles scrolling sideways when it doesn't fit. The tiles pass touches on to the row and the tab they sit in, so a swipe that starts on a tile scrolls (sideways along the row, or up and down the tab) instead of being swallowed by the tile; a tap still picks it. Beside the plaza (under it on a tall screen) is a panel on the machine's black glass (the start screen is the machine's, see docs/LORE.md): TABLE OF SALEM and "> simulation: salem, 1692", your name ("subject name"), a row reading [host] or [key] [join], and "practice evaluations", which opens the minigame tester (`scenes/main/minigame_tester.tscn`). The tester lists every minigame in `skill_checks/` and plays the one you pick in the same panel, at the same size, as at night, with no server. Played for real it rolls with the chance the game reports, the way the server would, and a log on the right shows what it reported and how it rolled; tick practice to play with nothing riding on it. Night, at the top of the list, plays a whole night the way a player lives it: Choose your action, then Roleblocks, Actions 1/2 and Actions 2/2 at the server's timings (8 seconds for roleblocks, 10 an action round), with the real overlay picking games from its real pools. Each night you either attack in the first action round, or do an action (its skill check falls in Roleblocks or Actions 1/2) and get attacked in the first action round you're free; every other stage is the practice game, which carries on between stages. The fights use the server's own fight rules: `PracticeFight` (`rust/crates/webgame-godot-rust/src/practice_fight.rs`) wraps the `Duel` from `webgame-game`, so strikes, grabs, guards and staggers time out exactly as online, against a bot (`scripts/minigame/practice_night.gd`) that reacts after a third to two thirds of a second, and now and then misses a move entirely, so it can be beaten. The morning's summary shows in the panel when the night ends. Fight, under Night, is practice for just that: three fights against the bot back to back, each going on until a knockout, attacking then defending then attacking, each named in the header, ending with how many you won. As on the town's clock, which past choosing shows only "Night N" with no stage name or timer, the header never says which stage is playing, so the night's cycle stays hidden and the panel is all you see. A skill check that counts, or a fight, opens with a 3 second countdown in the middle of the panel ("> evaluation" with the game's name, or "> confrontation"), with the game frozen and hidden until it ends, so it's clear when something rides on it; practice has no countdown. The server adds the countdown (`MINIGAME_INTRO_MS` in the protocol, `minigame_intro` in its timers) on top of every minigame stage, so it never takes from the time to play. The controls for the picked game show on the right, again starts it (or the night) over, and back or Escape returns to the start screen. The tester is the machine's screen too, titled "evaluations". The customizer is laid out for 1280x720 and scales smoothly to the window. The start screen, the town and their HUDs are laid out in units where the window's short side is 180, so a 16:9 window is 320x180 units (6 pixels each at 1080p) and a portrait phone is 180 units wide; the camera draws the pixel art at a whole number of screen pixels per art pixel. `scripts/ui/screen_scale.gd` sets both. Lobbies live on the game server, so start it first (`just play`, see [Game server](#game-server-and-test-client-rust)). The customizer (`scripts/wardrobe.gd`, which `customizer.gd` extends with save and cancel) is the machine's "subject setup": black glass over a faint grid, in its type and lower case. It shows your character on a projection pad that the arrows turn around, and groups the choices into body, face, outfit, gear, pet and house tabs, where each item is a picture tile of that item on your current body. On the House tab you pick your house's roof, facade and yard, and the preview switches to the house with your character in the yard. The house is saved with your profile and sent along with your look. Creating or joining takes you to the town. You arrive in the same spot by your house as on the start screen, facing the same way, and the camera glides from where the start screen framed you to the middle of the town's part of the screen, and the checkerboard floor dissolves from your house outward into the town, as if your house stayed put and the town formed around it (if that spot is inside a house's walls, you can walk out through them). In the town you walk with WASD or the arrow keys. On a touch screen, put a thumb anywhere on the town and drag to walk. To try that on a desktop, turn on Project Settings > Input Devices > Pointing > Emulate Touch From Mouse.

The town is a cul-de-sac with 15 lots around it, one per player, since a lobby holds 15. Inside the road loop is a small park with a paved plaza and the podium in the middle. The ground is painted in code by `front/scripts/cul_de_sac.gd`, and every size (the map, the road, the park, the ring of houses) is a constant at the top of that file, sized to the 32px characters. The town scene places the houses, podium, spawn point and map edges from those constants, so changing one keeps everything lined up. Characters in the town are drawn at 1.5x (the `scale` on the Character node in `scenes/main/player.tscn` and `remote_player.tscn`) so people read clearly next to the houses; the lobby and customizer previews stay at their own size. Lots fill in join order, clockwise from the road in, and each player's house is the one they picked in the customizer. Any layer they never picked (yard, facade or roof) gets a random style, seeded from the lobby code and the player's id so every client draws the same house. Empty lots show a For Sale sign.

In the town, each house is labeled with its owner's number and name; a player's number is how commands name them. The HUD is made for phones first, and for a game played around one table, out loud, with each phone as an assistant. It has three parts, side by side on a wide screen and stacked on a tall one (an `AspectFlowContainer`): the clock and the town's code on one sheet (with the chat under it on a wide screen), the town, and the roster with the Last will button under it. A wide screen reads [clock, chat | town | roster, buttons]. A tall one reads, top to bottom: the clock, the town with the chat as a sheet over it, then the roster (at most a third of the screen; its rows scroll) and the buttons. The buttons are the Last will (a paper and quill) and the role card (an ID card). The sheet is open by default, with a Chat tab on its top edge: drag the tab down to uncover the town and walk around, and up to bring the chat back (a tap does either). While the chat is down the tab counts new lines. During a night minigame the sheet slides down and the roster steps aside, but the tab stays, so the chat can be pulled up over the minigame to read what happened. The town is drawn behind the HUD, and the camera keeps you in the middle of the part the HUD leaves open.

- **The roster.** A parchment sheet (see [docs/DESIGN.md](docs/DESIGN.md)). At the top, what to do now as a title ("The Town Votes", "Night", "Judge the Accused"), with the votes a trial needs in wax under it, and the buttons that stand alone: Guilty (wax) / Innocent (verdigris) / Abstain during a trial, Cancel, Unvote, a night ability with no target, and before a game the host's Start game, sealed in wax, enabled once 4 players are in. Then a row per player, each at least 14 units tall to tap: their number in a circle of their seat's dye (`SeatBadge`, the same in the chat), their name, you in woad blue, and that player's buttons: a ballot-box icon to vote while voting (wax red once it's your vote), Choose for your own night ability or the Jailer's pick, and a whisper icon by day. Nobody can whisper to or from someone on trial, during their defense, judgement or last words, so the icon isn't there for them then. The dead are ash grey and struck through, their badge faded, with the role their death revealed (everyone's role shows once the game is over). While voting, each player's votes sit beside their name in wax ("2 votes"). That note, like the revealed role, "away" and "host", is never cut short; a long name is trimmed with an ellipsis instead. Your current choice shows filled with ink, and Cancel or Unvote takes it back. A button sends the same command as typing it, so the log shows the result either way. Nothing on the roster gives your role away to someone looking at your screen: your role isn't written, your ability's prompt is just Night (Day for the Jailer's pick), and its buttons say Choose (or Use, for one with no target) rather than its name; the role card has it.
- **The clock.** A parchment sheet at the top: a sun or moon, "Day 2" or "Night 1", the time left (wax red for the last five seconds) and the stage under it (Discussion, Voting (2 trials left), Defense: Bram, Judgement: Bram, Last words: Bram; at night only the choosing stage shows). Under a rule is the town's code with a copy icon (the code reads Copied for a moment) and a leave icon, which asks again inline: the first tap turns it wax red and the row reads "Tap again to leave" for 3 seconds, and only a second tap leaves (a phone's echo of the first tap, within 400 ms, doesn't count).
- **The chat.** Always open: a log of everything that happens, and a box to type in. People talk out loud, so for them it's mostly a record; the box is how terminal bots talk. It's the machine's log of the session, so it's on see-through black glass in monospace (the town shows behind it on a phone), and lines are colored by kind: what players said in light grey, led by the speaker's seat badge (so "Bram (2): hi" shows as the 2 badge and "Bram: hi"), whispers (and the notice that someone whispered) in cyan, game updates (results, deaths, votes) in amber, and the machine's own lines (the lobby, the connection, errors, help) dim after a `>`. The send button is an envelope icon. The screen already shows the players, your role and what you can do, so the log leaves those out ("Ada joined.", "The game begins.", "Voting is open.") where the terminal client prints the lists and the commands (`State::app` in `webgame-client`).
- **The role card.** Your role on a torn parchment card in the middle of the screen (`scripts/hud/role_card.gd`): a wax seal in your faction's color with its initial, the role's name and category, its ability and goal (and an Executioner's target or the Mafia's team). It shows on its own when a game starts, and the role button beside the Last will button opens it any time; the close icon, Escape or a tap outside closes it. The box doesn't show which channel plain text goes to (town, jail, mafia or dead), since that would give your role away to anyone looking at your screen. Press Enter to type and Enter again to send (Escape goes back to walking). The commands are the same as the terminal client's (`/vote 3`, `/target 2`, `/will ...`; `/help` lists them).
- **Typing.** Whispering and writing your will happen in a text box that opens in the upper middle of the screen, clear of a phone's keyboard (`scripts/ui/text_prompt.gd`): a parchment page with a ruled line to write on, Cancel, and a wax seal to send or save. Whisper on a player's row opens it for the message. The Last will button (under the roster, while you're alive in a game) opens it for your will, with Paste to bring one in from the clipboard. The start screen's name and lobby code boxes always open it, and the lobby code's has Paste, for a code someone sent you. On a touch screen the chat box opens it too, while the typing test, which has no box to tap, takes the on-screen keyboard itself and moves to the top of the screen, above the keyboard, with the chat put away until it's done. On the web, Godot types through a hidden text box on the page that it focuses a frame after your tap. Some iPhones only open the keyboard for a box focused during the tap itself, so they ignored that and the keyboard never came up. A small script in the web export's `html/head_include` (in `front/export_presets.cfg`) focuses that box again as the finger lifts, which counts as part of the tap. It also sets the box's font to 16px, since iOS zooms the page into a text box with a smaller font. An iPhone won't open its keyboard for a box that takes focus by itself, so on a touch screen the test says "tap here to type" until the first letter, and every tap on it asks for the keyboard again (which also brings it back after the phone puts it away).
- **Dropped connections.** Phones drop the connection when the browser goes to the background. The game keeps you where you are, the clock fades and stops, a notice in the machine's voice hangs at the top of the town ("desync detected, resyncing"), and it tries to get back into the lobby, under the same name, every 3 seconds for 90 seconds (`RECONNECT_SECONDS` in `session.gd`). The server holds your seat meanwhile: for the rest of a game, or for 90 seconds before one (`RECONNECT_GRACE` in `lobby.rs`), and only closes a lobby once everyone has been gone that long.

Dead players' houses go grey. At night the town is candlelit: a warm pool of light where it shows through the HUD, dark toward the edges, and the parchment panels turn candlelit with it. The dead are ghosts: while a game runs the living can't see them, and the dead see each other and themselves faded. Everyone shows again once the game is over.

After the night's actions lock in, a panel over the town shows your minigame for each stage (see [How a game runs](#how-a-game-runs)), and you don't walk while it's up. A skill check, the minigame your night action's chance rides on, is one of the kinds in `skill_checks/`, picked at random by weight:

- **Timing Wheel:** press Space or tap when the needle is in the gold zone, five times. The pips under it show your hits.
- **Typing Test:** type the words shown, Space after each.
- **Flappy Bird:** Space, Up or a tap flaps. Each of 5 pipes flown through is a fifth of the chance, and crashing ends it.
- **Flappy Golf:** flap a golf ball over the course into the cup. Every hole is new: a random mix of hills, dips, flat-topped mesas and bumps, sometimes played right to left, and on about half the holes a floating block or two that the ball bounces off and can roll along the top of. The ball bounces off the slope it lands on and loses the speed it hit with, so it can't ride up a hill; on the ground, gravity speeds it down slopes and slows it up them until friction stops it. Left/A and Right/D (or a tap on that side) flap that way, Up/Space flaps straight up. Holing out in par (3) or fewer is a sure pass, and each flap over par takes 20% off (never below 20%).
- **Fruit Ninja:** swipe across the fruit with the mouse or a finger. Each of 8 fruit sliced is an equal share of the chance, and slicing one of the 2 bombs ends it on the spot.
- **Blackjack:** one hand against the dealer from a 2-deck shoe. H, Left or Space hits; S, Right or Enter stands; or tap the buttons. While you decide, it shows the odds that hitting busts you, counted from every card you haven't seen. A win is a sure pass, a push is 50% and a loss fails (tunable in `blackjack.tres`).

The four arcade games (Flappy Bird, Flappy Golf, Fruit Ninja, Blackjack) share `ArcadeCheck`, which fits their 140x100 play field to the panel; each keeps its rules in a model class (`FlappyGame`, `GolfGame`, `FruitGame`, `BlackjackGame`) tested in `tests/arcade_games_test.gd`. Every minigame plays by touch as well as keys: a tap is a click (flap, flip a card, hit or stand on Blackjack's wide buttons, tap a side of the golf course to flap that way), Fruit Ninja slices with a finger swipe, and the typing test brings up the on-screen keyboard on phones. Godot also turns each touch into a made-up mouse click, so `SkillCheck.is_tap()` and Fruit Ninja skip events from `InputEvent.DEVICE_ID_EMULATION` and one tap counts once. Each kind is a `SkillCheckDef` resource (a `.tres` file) that names the scene that plays it (in `scenes/skill_checks/`, its root extending `SkillCheck`) and holds its tuning, like the dial's presses, zone width and speed. A harder variant is another `.tres` with different numbers. To add one, list its `.tres` in the minigame overlay's Skill Checks in the inspector. A fight shows you and your masked opponent: J (or Z) strikes, K (or X) grabs, and L, C or Space guards, or tap the buttons. A guard is a tap: it takes 0.7 seconds to come up (`GUARD_RAISE_MS`, half a strike's windup), so it blocks a strike seen coming but not one about to land, then stays up for 3.2 seconds (`GUARD_MS`) and drops on its own. After a guard ends (dropping, dropped, grabbed through, or lowered to attack) another can't be raised for 1.4 seconds (`GUARD_COOLDOWN_MS`), the Guard button greys out meanwhile, and a guard pressed just before then waits and goes up as soon as it can. So a guard can't be held all fight: a strike started as one drops always lands. A strike (1.4 second windup) hits an open fighter but bounces off a guard and leaves you dazed for 2.2 seconds; a grab (1.6 seconds) breaks a guard and misses an open fighter. A grab is only a little slower than a strike, so striking out of one takes a read, starting the strike almost as they start the grab; seeing it coming and then striking is too late, so holding a guard all fight gets grabbed. In short: guard a strike, strike a grab, grab a guard. A bar over each fighter fills as their move winds up so it can be answered in time, a press made while you're winding up or dazed is held for a moment and sent as soon as you're free, and HIT!, GRABBED!, BLOCKED! and MISSED pop up over the fighters. Each fighter takes 3 hits and a fight goes on until someone loses them all, so it shows no timer; the action round itself lasts 10 seconds, which is how long everyone else plays, and runs on while a fight does. Every minigame timer counts whole seconds.

Everyone else gets a practice game with nothing riding on it, picked at random from the overlay's Practice Checks: any of the games above except the dial, or Card Memory (`skill_checks/memory.tres`). In practice the arcade games keep going (a crash or a finished hole, wave or hand starts the next) and keep a score. In Card Memory 16 cards show face up for two seconds, then turn over, and you turn two at a time (tap them, or move with the arrow keys and press Space) to find the 8 pairs. Pairs stay up, and clearing the board deals a new one. The practice game you get carries on from stage to stage through the night, as it was, until a skill check or fight that counts interrupts it; the next practice after that is picked at random again, and so is the first one each night, never the game you were just playing. Once your skill check is decided it carries on as practice until the stage ends, and once your fight is decided you get a practice game.

The client connects to `ws://127.0.0.1:9090/ws`. To use another server, pass it after `--`: `godot --path front -- --server=ws://192.168.1.20:9090/ws`. In a browser it connects to port 9090 on the host that served the page (`wss://` when the page is on `https://`, which the server doesn't support yet). To play several Godot clients on one machine, use `just clients 4` (up to 15), or run one window at a time with `godot --path front -- --name=Bram --join=ABC234`.

Everyone in the lobby walks around the same town. Each client sends its player's position about 15 times a second while it changes, and the server passes it on to the others, who glide each character toward its latest position. A player's look from the customizer is sent on joining, so others see them as they dressed. A newcomer stays hidden until their first position arrives, so they don't flash in front of their house before jumping to where they are; a terminal player, who sends none, shows in front of their house after a second. Dead players show faded. Movement is only relayed, never stored, and other players don't block you.

| Path | What it is |
|------|------------|
| `scenes/main/` | The game's scenes: `lobby`, `customizer`, `town`, plus what the town places: `player` (you), `remote_player` (everyone else), `house`, `hud` (players, clock, chat and actions) and `minigame_overlay`, and `minigame_tester` |
| `scenes/test/` | Standalone test scenes: `main` (walk around a field) and `wardrobe` (character preview with no save) |
| `scripts/hud/` | The town's HUD, one script per panel (`roster`, `phase_clock`, `chat_panel`, `role_card`) |
| `scripts/ui/` | The design system (`design/`: `Palette`, `Tokens`, `Fonts`, `UiTheme`) and its components (`kit/`), see [docs/DESIGN.md](docs/DESIGN.md); `TextPrompt`; `ScreenScale` sets how each screen scales to the window |
| `scripts/house/` | House drawing: `HouseCatalog` finds house art on disk, `HouseAppearance` holds one house's styles |
| `scripts/autoload/` | Globals available in every scene: `PlayerProfile` (the saved character and name, kept in Godot's `user://` folder) and `Session` (the connection to the server and the current lobby, through the Rust `GameClient`) |

To run one scene by itself, open it and press F6.

From a terminal, the commands below use `godot` to mean the Godot executable. Either add it to your PATH or replace `godot` with its full path.

- Open in the editor: `godot -e --path front`
- Run the game: `godot --path front`
- Run the walking test scene: `godot --path front res://scenes/test/main.tscn`

`front/assets` is a symlink to the top-level `assets/` folder, so sprites appear in Godot as `res://assets/...`. On Windows, Git checks symlinks out as plain text files unless symlink support is on. Enable Developer Mode, then clone with `git clone -c core.symlinks=true ...`. Godot writes a `.import` file next to each image; commit those.

### Web export

The web build compiles the Rust extension to WebAssembly, which needs extra tools.

1. One-time setup:
   - Add the nightly Rust toolchain and the pieces the web build uses:
     ```sh
     rustup toolchain install nightly
     rustup component add rust-src --toolchain nightly
     rustup target add wasm32-unknown-emscripten --toolchain nightly
     ```
   - Install Emscripten 3.1.74 with [emsdk](https://github.com/emscripten-core/emsdk) (`./emsdk install 3.1.74`, then `./emsdk activate 3.1.74`), and set `EMSDK` in `.env` to the emsdk directory. The installer needs Python 3.10 or newer; if the system `python3` is older (macOS ships 3.9), point `EMSDK_PYTHON` at a newer one for the install, like `EMSDK_PYTHON=/opt/homebrew/bin/python3.13 ./emsdk install 3.1.74`. emsdk brings its own Python after that.
   - In the Godot editor, Editor > Manage Export Templates > Download and Install.
2. Run `just export-web`. It builds the extension in release mode, then exports the game to `front/build/web/index.html` (gitignored).

   Exporting from the editor (Project > Export) or testing with Remote Debug > Run in Browser also works, but neither rebuilds the extension; they copy whatever `.wasm` is already built. Run `just build-web release` before an editor export, or `just build-web` before Run in Browser, which uses the debug build.
3. Browsers won't run the export from a `file://` URL, so serve `front/build/web` with any static file server and open it over `http://`. The preset turns thread support off, so the server doesn't need special COOP/COEP headers. Any static host (itch.io, GitHub Pages, Netlify) works the same way. The Rust extension is built single-threaded to match; turning thread support on in the preset would also need a threaded build of the extension.

## Game server and test client (`rust/`)

The game itself (lobbies, roles, days and nights, chat, voting, last wills) runs on a Rust server. You play it from the Godot client, from a small terminal client, or both in the same lobby. They speak the same protocol and share the same client code.

| Crate | What it is |
|-------|-----------|
| `webgame-protocol` | Every type that crosses the network, defined once: ids, roles, phases, chat channels and their rules, and the `ClientMessage` / `ServerMessage` enums. Messages are encoded with [postcard](https://docs.rs/postcard) and sent as WebSocket binary frames. It has no OS dependencies, so the Godot extension can use it, including in the web build. |
| `webgame-game` | The rules engine: setting up a game, the day and night cycle, the night calculator, and win conditions. It does no networking and reads no clock (time is passed in), so whole games run in tests in milliseconds. |
| `webgame-server` | The server: a WebSocket endpoint at `/ws` (and `/health`), one task per lobby that owns its game, and a SQLite file that records users, lobbies, games and every message each game sent. |
| `webgame-client` | What a client knows about the game, kept up to date from server messages, how each message reads as text, and how a typed line like `/vote 3` becomes a message. Both clients use it, so they agree on the rules and describe the game the same way. |
| `webgame-cli` | The terminal client. |
| `webgame-godot-rust` | The GDExtension Godot loads: the `StateMachine`, `AspectFlowContainer` (a BoxContainer that lays its children out in a row on a wide screen and a column on a tall one), and `GameClient`, the node that talks to the server over Godot's WebSocketPeer (which also works in the web export) and gives GDScript methods and signals. |

### Playing a test game

Start the server, then open one terminal per player (a game needs at least 4, at most 15):

```sh
just play                            # the server, with short phases
just cli --name Ada --create         # prints a lobby code, like ABC234
just cli --name Bram --join ABC234   # and the same for Cleo, Dev, ...
```

Add `--fight-bot` to a terminal player to have it play its night fights for itself (striking, guarding and grabbing with a human-ish reaction time), so a Godot player can fight bots. Without it, a terminal player's fights are rolled.

Players can also join from the Godot game (`just run`) by typing the lobby code, and Godot and terminal players can share a lobby. To play several Godot players on one machine, `just clients 4` opens four windows tiled in a grid (up to 15), with Ada hosting and the rest joining her lobby. Press Start game in Ada's window, and Ctrl-C closes them all. A single window takes the same options after `--`: `godot --path front -- --name=Bram --join=ABC234`, or `--create` to host. The player who created the lobby types `/start` (or presses Start game in Godot). `/help` lists every command. Players are named by their number from `/players`, so `/vote 3` votes for player 3. Plain text goes to whatever chat you can use right now: the lobby, the town square by day, or by night the jail, the Mafia, or the dead.

| Command | What it does |
|---------|-------------|
| `/create`, `/join CODE`, `/leave`, `/start` | Lobbies. Only the host can start. |
| `/w N text` | Whisper to player N during the day. Everyone sees that you whispered, only N sees what. |
| `/vote N`, `/unvote` | Vote player N up for trial. |
| `/guilty`, `/inno`, `/abstain` | Judge the player on trial. |
| `/jail N` | (Jailer) pick tonight's prisoner, during the day. |
| `/target N` | Use your night ability on player N. A lynched Jester haunts with it too. |
| `/target N M` | (Copycat) use player N's night ability on player M. Or pick in two steps, like the buttons do: `/copy N`, then `/target M`. |
| `/alert`, `/vest`, `/ignite`, `/execute` | Night abilities with no target: Veteran, Survivor, Arsonist, Jailer. |
| `/cancel` | Take back tonight's action, while actions are still being chosen. |
| `/roll` | Have the server decide your minigame at random (a skill check passes 75% of the time, a fight is a coin flip). The terminal client does this by itself, since it can't show minigames; only servers run with `--rolls` (or `--fast`) allow it. |
| `/will text` | Set your last will, shown to everyone when you die. Write `\n` for a new line. `/will` alone shows it. |
| `/role`, `/roles`, `/players` | Your role and team, the game's role list, and who is alive. |

The server takes `--fast` (short phases, and turns on `--rolls`), `--rolls` (minigames may be rolled, which the terminal client does, so CLI bots can play on a server with normal phase lengths: `just server --rolls`; any client may roll, so only use it where you trust the players), `--seed N` (the same roles every game, given the same players), `--port` (default 9090), `--host` (default 127.0.0.1) and `--db` (default `webgame.db` in the directory it runs from, which is `rust/` under `just`; gitignored). `just server` runs it with normal phase lengths. To look at what a game recorded: `sqlite3 rust/webgame.db 'select * from games'`.

There is no authentication yet. A username is the whole identity: the same name always gets the same user id, which is how a player who drops reconnects to their seat (join the same code with the same name). While a name is connected to a lobby, nobody else can join it under that name. The server only listens on localhost by default, and doesn't check the `Origin` of WebSocket connections, so don't expose it to the internet as it is.

### How a game runs

- **Cycle.** Day 0 is a short introduction, then Night 1, Day 1, Night 2, and so on.
- **Days.** Discussion, then voting. A player voted up by a majority of the living goes on trial: they make a defense (only they can talk), then everyone judges them guilty, innocent or abstains. Votes to put someone on trial are open: each vote or unvote puts a line in the chat saying who voted for whom ("Ada (1) voted for Cleo (3).", or "took back their vote"), followed by the tally. More guilty than innocent votes means last words, a lynch, and the day ends. Otherwise voting resumes. After 3 trials, or when voting time runs out, night falls.
- **Joining late.** Joining a lobby whose game has started, while a seat is free, makes you a spectator: dead from the start, with no role, watching and talking in the dead chat. You're left out of the results, and play from the next game.
- **Nights.** Players pick their actions at nightfall (12 seconds, 15 on `--fast` servers), and then they lock. The rest of the night runs in stages that always take the same time: roleblocks (8 seconds), then two action rounds (10 seconds each), each with a 3 second countdown on top, so a night is under a minute. Roleblocks go first because one that works takes away its target's minigames for the rest of the night. Every other skill check is played at once in the first action round, since all actions resolve together at dawn and none needs another's result first. A fight goes in the first action round where both fighters are free, so someone with their own skill check, or a second attacker on the same victim, fights in round 2. In each stage every living player plays one minigame. Whoever acts in that stage plays a skill check, a short game on the client such as five presses on a timing dial. The client reports the chance the action should work (the dial reports hits out of five, so 3 hits is 60%), and the server rolls with it once the player is done, or with the last chance reported when the stage ends (none counts as 0). Only `rust/crates/webgame-game/src/check.rs` turns what the client sends into that chance, so the server can judge checks itself later by changing just that file. Failing means the action does nothing, though they still visit their target (a Lookout sees them, a Veteran on alert shoots them). An attack by the Mafia, a Serial Killer, a Vigilante or a lynched Jester is a fight between attacker and victim, who don't learn who the other is; the attack only goes ahead if the attacker knocks the victim out, and even then heals, guards and defense still apply. A fight isn't decided by the clock: if one is still going when its round runs out, the round quietly runs on a second at a time until someone is knocked out (the victim wins a double knockout). Only a fight still going two minutes past its round, where both players have stopped playing, goes to the victim. Jailer executions and Arsonist ignitions are skill checks. Everyone else plays a game with nothing riding on it. Once the stages are done the server works out what happened all at once: jailing, then roleblocks, then protection, then attacks, then investigations. Each player gets their own results, and the morning announces who died, with their role and last will.
- **Chat.** Lobby chat; the town square by day; whispers by day; jail chat (the Jailer and their prisoner, who doesn't learn who the Jailer is), Mafia chat and dead chat by night. A living Medium hears and speaks to the dead at night. Dead players can always read the town square and dead chat.
- **Winning.** Town wins when every Mafia member and neutral killer is dead. The Mafia wins when it is at least as big as everyone else and no neutral killer is left. A Serial Killer or Arsonist wins as the last one standing. A Jester wins by being lynched, an Executioner by getting their target lynched, and a Survivor by being alive at the end; they win alongside whoever else wins. Three day/night cycles in a row with no deaths end in a draw.
- **Role list.** Roles come from a list that grows with the player count (Town of Salem's ranked list, trimmed): with 4 players it is Mafioso, Town Investigative, Town Protective, Neutral Evil; with 15 it adds Town Support, another Town Investigative, Godfather, a random Town role (the Jailer's slot, while the Jailer is out of play), Town Killing, a random Mafia role, a Neutral Killing role, three random Town roles and one of anything. The Jailer is out of play for now: its code is all still there, but `Role::in_play` keeps it from being rolled, so no game deals it. When the Godfather dies the Mafioso takes over, and when there's no Mafioso another Mafia member becomes one.

## Tests

`just test` runs everything. `just test unit` runs only the Rust unit tests (`cargo test`, so extra arguments go to cargo), and `just test godot` runs only the Godot integration tests. The Rust tests include every night interaction (`rust/crates/webgame-game/tests/night.rs`), scripted games, and a server test where four WebSocket clients play a whole game (`rust/crates/webgame-server/tests/server.rs`).

Integration tests live in `front/tests/` and use [GdUnit4](https://github.com/godot-gdunit-labs/gdUnit4), which is vendored in `front/addons/gdUnit4`. They run in headless Godot with `--fixed-fps 60`, so every frame advances by exactly 1/60 s no matter how long it takes. To run one suite, pass GdUnit4's options: `just test godot -a res://tests/state_machine_test.gd`. You can also run them from the GdUnit4 panel in the editor. Reports are written to `front/reports/` (gitignored).

`front/project.godot` sets `gdunit4/report/godot/push_error=true`. Rust panics are reported as engine errors, and without this setting GdUnit4 doesn't count them as failures, so keep it on.
